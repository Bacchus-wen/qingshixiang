# AI 团队工作流(新游戏 的实际做法,2026-10-19 整理)

## 一、角色

| 谁 | 做什么 |
|---|---|
| 用户 | 定方向;批准一切生成和花钱的事;看预览;最终拍板 |
| Claude(Opus 5.5,主会话) | 统筹、主要实现、组织审查、向用户汇报;唯一在沙箱外跑浏览器 / Blender / Vite 做实际验收的一方 |
| Codex(本机 CLI,gpt-6-astra) | 通过任务板接活:主要是只读审查(看截图,给批判和分数),也可以接有路径范围的写任务;不启动浏览器、Blender、Vite |
| Grok | 原来做调研和第二意见。**2026-10-19 订阅过期,不再派**;需要两个视角时,给 Codex 派两份分工不同的任务 |

- 不用 ChatGPT 的任何功能(网页、App、Codex Cloud、连接器与同步、OpenAI 生图),防止项目信息同步或泄露。Codex 只通过本机 CLI 和任务板使用。
- 三家共同遵守项目根目录的 `AGENTS.md`(技术栈、目录归属、硬性禁止、进程安全)。

## 二、任务板(team-sync)怎么派活

- 三家看不到彼此的聊天,**唯一的共同事实是 `<项目>/.agent-tasks/`**。一个开机自启的"传达员"服务把任务单送给对应的 AI,再把结果写回。
- 项目必须放在 `~/Games/<名字>` 或 `~/Projects/<名字>` 下(传达员只监视这两处)。所有项目的任务板可以在浏览器看:http://127.0.0.1:8765。
- 命令:`python3 "$HOME/.local/opt/agent-team/team.py"`(下文写作 `team`)。

步骤:
1. 开工先看板:`team board --project "<项目>"`(进行中的任务、被占用的路径、最近日志)。
2. 自己改文件前先占路径:`team claim --project "<项目>" --from claude --paths "src/ui/**" --note "在做什么"`;改完 `team release`。
3. 写任务单(放在 `.agent-tasks/` 下)。对方看不到聊天,任务单必须自成一体,写清六件事:背景;要做什么;能读、能改哪些路径;能不能联网、能不能调用付费生成;怎样算做完;交回的格式和长度。
4. 派发:
   ```bash
   team post --project "<项目>" --from claude --to codex --title "一句话标题" --task-file "<任务单>" --id <短名字>
   ```
   写任务加 `--write --paths "<它能改的路径>"`。`--to others` 会派给另外两家(Grok 已停用,所以现在一律写 `--to codex`)。
5. 取结果:`team wait --project "<项目>" --id <名字> --show`。状态不是 `done` 时读 `.agent-tasks/<名字>/meta.json` 和 `raw.log`,不原样重派。
- 写任务在项目的**副本**里改;只有全部改动都在 `--paths` 之内、原文件期间没被别人动过,才一次性带回(全有或全无)。
- 实测:只读审查一般一分钟左右交回(r24 那轮 56.7 秒)。

## 三、一轮"实现—审查"

> 最严格的视觉审查:具体做法、自动检查和任务单模板见 `docs/VISUAL-REVIEW.md`。

1. Claude 改代码。
2. 自动试玩一整遍:`node tools/play-shop.mjs --speed 2`(用 Playwright 自带的 Chromium,按故事自己的时钟截关键帧,同时记录声音电平,拼成一张总图);单个镜头用 `node tools/shot.mjs <镜头名>`。**试玩期间不改文件**(开发服务器会热更新、把页面重载)。
3. Claude 先自己看图、写自我批判:**先查模型**(软塌、粘连、悬空、穿插、卡顿),再看光、构图、节奏。
4. 整理审查包 `docs/review-shop/rNN/`:`story-*.jpg`(整遍按顺序的实时截图)、`detail-*.jpg`(特写)、`ref-*.jpg`(最初定下的目标画面)。
5. 给 Codex 派两份只读审查,分工不同:
   - **画面与模型**:Tripo 模型是不是主角、看得出的模型问题、悬空穿插、可执行的改法,打"作为 Tripo 模型展示"的分。
   - **故事与体验**:观众能不能读懂、哪里无聊或迷路、最影响"打动人"的问题,打"作为一段动人的短片"的分。
   - 任务单固定写明:相对上一轮解决了什么、没解决什么、变差了什么;最多几条,按影响排序,每条给可执行的改法;只读、不联网、不调用付费生成、不启动浏览器 / Blender / Vite;中文,限字数。
6. 按反馈改,进入下一轮。每轮分数记进交接文档(例如 r18:4/4 → r24:模型 6.2、故事 7.5)。

验收标准:
- 对照**最初的参考画面**,不是"比上一版好"。
- 同一个问题被多次指出,必须真正替换或重做,不能挪开或藏起来。
- 不把批判限制成"一小时能改的参数",否则模型问题会被绕开。
- 后台 Claude 子代理读图会卡死,看图批判一律派 Codex;主会话自己读图没问题。

## 四、审批:什么必须先问用户

### A. 生图、改图、生视频、生 3D 模型(任何工具都算)
包括 Claude 自带的工具、公司素材中台 `vmc`、`game-assets` 里的工具、Tripo,以及其他任何接口或脚本。顺序:
1. 先问走哪条路(素材中台 / 自带工具 / 其他)。
2. 再问用哪个模型、什么参数(尺寸或比例、张数或条数、时长、透明底、要不要声音),同时给推荐和理由。可选的模型以当时实际查到的为准(`vmc models image`)。
3. 把准备用的提示词给用户看。
4. 用户没说的项不自己填;只有用户这次已经点名的项可以不问。
5. 用户答完,给出计划(要花多少配额或费用),用户同意才生成。

素材中台的操作顺序:
- 先**不带 `--yes`** 跑一次,拿到计划(模型、数量、配额前后、费用;退出码 5 = 需要确认),给用户看。
- 用户同意后,**同一条命令**加 `--yes` 再跑;参数改了就是新计划,要重新确认。只想看花费用 `--dry-run`。
- 结果用 `--out <项目>/assets/generated/vmc` 只下载到本地,不用 `--folder`。
- 派出去的无界面任务没法问用户:除非任务单写明"用户已确认"并给出完整命令,否则不生成。

例子(2026-10-19 的对街照片):
1. 用户先选做法:两张对应的街景画。
2. Claude 列出模型、尺寸、张数和提示词,附上推荐。用户选了 gpt-image-2.5-sunburst、max、3840x2160、两种各出 2 张挑 1。
3. Claude 先拿计划:配额 0 → 2。确认后加 `--yes` 生成"现在"2 张,挑出 1 张。
4. 用挑出的那张做参考图再拿计划:配额 2 → 4。确认后加 `--yes` 生成"从前"2 张,再挑 1 张。
5. 一共 4 张,只下载到本地项目。

### B. 公司素材中台和 Tripo 账号(公司共用,不做危险操作)
- 只做:查看、搜索、查配额和价格、用户确认过的生成、把结果下载到本地项目。Tripo 生成用 `--visibility private`。
- 一律不做:删除、覆盖、移动、重命名任何素材或文件夹;往公司素材库或共享文件夹上传、转存(除非用户这一次明确指定了文件夹);分享、发布、提交审核、评论、发通知;修改共享内容(Skill 助手、可灵主体库等);改账号设置、权限、配额,创建或吊销令牌;批量下载公司素材。
- 拿不准某个按钮会不会影响别人,不点,先问。出了意外立刻停下告诉用户,不自己补救。

### C. 大的方向和要花钱的重做
- 例如:故事改成"看外面"、去掉身高刻度;5 个模型重新生成(约 300 Tripo 积分)。这些由用户决定。
- Claude 用选择题问:每题 2–4 个选项,推荐项放第一个并说明理由。不问"可以开始吗"这类问题。

### D. 不用问、但必须一直守的规矩
- 不推送到 GitHub,只在本地 commit。
- 不读 `~/Downloads/tripo_mv` 里的 `.env`。
- 不启动用户自己的 Chrome:截图和自动化只用 Playwright 自带的 Chromium。
- Blender 只用无界面模式(`-b`),脚本末尾 `os._exit(0)`。
- Codex 的沙箱里不启动 Blender、浏览器、Vite 或任何监听端口的服务。
- 自己启动的后台进程,任务结束前要关掉。
- 长时间无人值守前确认 Mac 接着电源(低电量休眠 caffeinate 挡不住)。

## 五、用户授权的连续开发

- 用户给出范围和时间(例如"继续开发后续的所有,中间不问"),Claude 就连续做、按轮审查,能自己定的事不打断用户。
- 即使在这种授权下,第四节 A、B、C 仍然要先问。
- 用户中途插话(例如这次的"重点应该看外面"),Claude 先停下手上的活,把需要用户定的点整理成选择题,其余照常推进。
- 汇报内容:做到哪一步、还剩什么、还要多久。长内容写进文件,聊天里只给摘要(用户的网关对太长的回复会报 524 超时)。

## 六、交付与存档

- **预览**:
  - 开发服务器 http://127.0.0.1:5173:改文件会自动刷新,不适合正式看。
  - 冻结版 http://127.0.0.1:5181:用 `node tools/serve-demo.mjs /tmp/demo-story 5181` 提供,不受改动影响。每轮改完、检查过以后才更新冻结版,并告诉用户。
- **文档**:
  - `README.md`:怎么运行、有哪些地址参数。
  - `docs/HANDOFF.md`:交接。
  - `docs/REPORT.md`:汇报、分数和性能数据。
  - `CREDITS.md`:素材出处与许可。
  - `docs/gen-log.md`:生成记录(模型、参数、提示词、任务 ID)。
- **存档**:本地 git commit,提交说明写清这一轮改了什么、审查给了几分。
- **跨会话记忆**:`~/.claude/projects/<项目>/memory/` 记用户的偏好和规矩(默认生图参数、Grok 停用、进程安全等),新会话自动读到。

## 七、一页速查

```
开工        team board
改文件前    team claim --paths … / 改完 team release
派审查      写任务单(六件事) → team post --to codex → team wait --show
每轮        改 → 自动试玩截图 → 自我批判(先查模型) → 审查包 → 两份 Codex 审查 → 改
生成前      问路线 → 问模型和参数(附推荐) → 给看提示词 → 给计划(配额、费用) → 同意后 --yes
中台账号    只看、只生成确认过的、只下载到本地;不删、不传、不发布、不改设置
要用户定    方向大改、花钱的重做 → 用选择题问,推荐项放第一个
交付        冻结版 5181 + HANDOFF / REPORT / CREDITS / gen-log + 本地 commit
```
