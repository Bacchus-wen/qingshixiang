**r21 第六轮严格批判｜result.md**

**结论：现在不适合拿来宣传 Tripo。** 问题已经超出“灯光不够好、参数还需调”。主角来源与宣传目标脱节，近景资产没有通过造型和接触关系验收，大量资源成本又花在观众看不清的背景上。用户说“没用心”，对应的是这些最终结果。

本轮只读查看了指定截图、参考图、源代码与 GLB 数据，没有运行构建、浏览器、Blender、Vite，没有修改文件。以下区分画面缺陷、静态证据和性能推算；不把推算写成实测。

**1．模型质量：最重要的模型，恰好没有承担起 Tripo 宣传任务**

`targets/robot.jpg` 的价值不只是雨水和灯光，而是清楚的装甲厚度、内部结构、磨损层次、自然坐姿，以及猫与机器人的重量关系。当前机器人保留了“大致轮廓”，丢掉了这些让人相信它存在的东西。

cybercity 两张参考帧虽然也有雾和泛光，但车辆、店面、人物与街道仍然形成连续空间。当前画面学到了霓虹和反射，却没有同等完成物体的尺度、摆放和材料。**把场景变暗，不等于让粗糙模型成立。**

**Tripo 资产的实际范围与审查边界：**

- `assets/models/v2/` 有 **32 个 GLB**：16 个普通道具、16 个 `m_` 模块。运行代码加载其中 31 种；`m_pole` 没有出现在模块加载清单中。
- 普通道具除上表外，还包括 `acunit`、`bicycle`、`bins`、`bottlecrates`、`cardboard`、`freezer`、`lightbox`、`lpg`、`meterbox`、`planters`、`scooter`、`stools`、`stove`。近景里能辨识红凳、灯箱、冰柜、踏板车等轮廓，但不足以逐一评价其拓扑或纹理；**这批资产没有得到足够的展示，不能因“已经生成”就算宣传成果。**
- `assets/generated/tripo3/` 保存 16 个模块原件及记录，对应 `balcony`、`balcony_open`、`window_ac`、`awning`、`watertank`、`stall`、`ac_cluster`、`roof_shack`、`cable_box`、`lightbox_wall`、`drainpipe`、`pole`、`fruit_stall`、`kiosk`、`lanterns`、`noodle_table`。
- 原件每个约 **179万—200万三角面、63—70 MB**；网页版本降至约 **1.86万—2.4万三角面**。部分接近削掉 99%。因此画面里栏杆、线缆、棚边变粗变黏，**不能未经对照就归罪于 Tripo 原始生成质量**；也可能是粗暴减面、贴图降采样和摆放共同造成的。
- 水箱、屋顶棚、排水管、电箱、面摊、报亭等，在这批截图里缺少可评判的独立近景。我不虚构“每一个都烂”的结论，但目前也没有证据证明它们通过了宣传级验收。

**必须重做的顺序：**

1. **P0：机器人主体与头部。** 这是作品的脸，也是目前最不符合宣传目标的资产。
2. **P0：猫。** 做出可信的蜷卧猫；做不到就删，不准继续以黑暗遮丑。
3. **P1：轿车。** 长时间位于光束主视角，必须有清楚的轮胎、玻璃、内饰、车灯与合理车门结构。当前 Tripo 车是一体 mesh，原有 `door_fl` 动画接口找不到，所谓“回忆中关门”没有真正接通。[details.js](/Users/wenbin/Games/新游戏/src/systems/street/details.js:61)
4. **P1：结尾破伞。** 留在前景就重做，不能用折纸简模收尾。
5. **P1：饮水机／水桶组合。** 先改掉输入中的错误承重结构，再生成。
6. **P2：盖布三轮车、最近一组阳台／空调窗。** 各选一个做到好，不要再扩充种类。
7. **P2：门主体。** 重点是空间结构和材质；刻度文字无需交给生成模型解决。

这不是要求把所有物件换成 Tripo。是要求**最值得被观看的几个物件，确实成为 Tripo 的好样本**。

**3．卡顿与体积：当前主要问题是解码后资源和渲染成本，不是一个 1.4 GB 的 dist**

|---|---:|
| `dist/` 全部 129 个文件 | **56.78 MB** |
| `dist/models/v2/` | **25.87 MB** |
| `dist/textures/cc/` | **10.24 MB** |
| `dist/models/crowd/` | **6.93 MB** |

| `dist/models/robot_k1.glb` | **2.76 MB** |

`vite.config.js` 会在构建结束移除 `dist/generated`。所以：

- 若“1.4G”来自浏览器任务管理器，应按**运行内存**诊断，不能拿 GLB 下载大小解释。
- 若来自交付文件夹，应检查是否把生成原件和工程一起交付。
- 当前 dist 已小于 500 MB，但这**完全不代表运行占用达标或普通笔记本流畅**。
- `docs/PERF.md` 仍记着“打包 6.7 MB”，明显不是当前资源版本，不能继续拿来证明 r21 性能。

**最大的内存／显存去向：**

**第一，Tripo 贴图解码，证据最直接。** 32 个 GLB 每个包含三张 1024×1024 图片，当前不是 GPU 压缩纹理。

按 RGBA8 与完整 mip 链估算：

`32 × 3 × 1024 × 1024 × 4 × 4/3 ≈ 536.9 MB`

实际默认加载 31 种，约 **520.1 MB**。克隆和实例共享纹理，不应按摆放次数再次相乘；但只加载一套，也已经很大。其他外置贴图若全部按同样口径计算约 292.4 MB，其中有未使用资源，人物图集还关闭了 mip，不能直接全算入当前显存。尽管如此，**常用图片资源达到数百 MB 是有文件依据的**。浏览器还可能保留解码图像、上传缓冲与其他副本。

**第二，全分辨率后处理。** 当前管线有颜色、法线、金属／粗糙度、速度四路 MRT，加深度；之后有 TRAA 历史、SSR、AO、DOF、Bloom、散射与横向拖光。

在 1920×1080 下，按当前 attachment 类型，主 MRT 加深度约 **58 MB**；TRAA 两张半浮点颜色图加历史深度又约 **41 MB**。还没算深度预通道、DOF、SSR、Bloom 等。窗口扩大到更高分辨率，成本按像素数增长。

最不该忽略的两个事实：

- **DOF 的 `bokeh=0` 不会停掉处理。** 当前 three.js 实现仍执行 CoC、模糊、近远场处理与合成，共七次全屏／降采样绘制。必须从管线中绕开，不能只把参数设为零。
- **low 仍创建四路 MRT。** AO、SSR 已关，法线和材质参数附件却仍保留；还保留 TRAA、Bloom、散射和拖光。[PostFX.js](/Users/wenbin/Games/新游戏/src/engine/PostFX.js:55)

**第三，几何、阴影和材质复杂度。**

- 当前机器人约 **20.6万三角面、207 个源 mesh**。身体运行时合并时转为非索引顶点，头部大量部件仍单独保留；不是“文件只有 2.76 MB，所以很轻”。
- 阳台和空调窗每种约 2.4 万面，实例化只减少 draw call，**不会免除每个实例的顶点、阴影计算**。全街一组实例还不利于细粒度剔除。
- 合并街道会把跨很长距离的网格绑在一起，降低视锥剔除收益。
- 机器人材质逐像素计算多层噪声、锈蚀、油污、划痕、水珠、流痕、凹凸与清漆。昂贵的计算最终却给出了廉价塑料观感。
- 雨在 WebGPU 默认 **60,000 粒子＋3,072 水花**；它更值得关注的是透明覆盖和填充成本，而不是这些粒子的存储大小。
- 体积雾与额外 16 步光束叠加，有重复的像素积分成本。VAT 人群确有浮点纹理成本，但相对上述贴图与后处理，**不是第一刀该砍的对象**。

**第四，自动降级并不可靠。**

WebGPU 支持就默认 high，没有区分独显与普通集显。降分辨率还要求 `frameMs > 20.5 && submitMs > 9`；GPU 异步执行慢时，CPU 提交可能仍很快，因此可能一直不降级。雨和风读取 URL 的 `q`，不是统一的 `ctx.quality`，也会出现引擎已经判 low、子系统仍按另一档运行。[Engine.js](/Users/wenbin/Games/新游戏/src/engine/Engine.js:109)

**降到 500 MB 以下的具体方案，按收益排序：**

| 改造 | 具体要求 |
|---|---|
| **GPU 纹理压缩** | 给 GLTFLoader 接入 KTX2Loader，GLB 使用 `KHR_texture_basisu`。颜色可优先考虑 ETC1S，法线／细节敏感图用 UASTC，并核验目标设备转码格式。JPEG 改 WebP 只减下载，不能解决同等尺寸纹理解码后的显存。 |
| **按镜头分配纹理** | 主角及核心门最多使用少量 2K 图集；近景车、三轮车等使用 1K；远景模块 512，最远处 256 或共享材质。法线与 ORM 不必和颜色图同尺寸。目标是**常驻纹理含 mip 控制在约 100 MB**，不是给所有物件统一三张 1K。 |
| **保留轮廓的减面与 LOD** | 机器人建议从 5万—8万面起做近景版本；车 1.5万—2.5万；猫按轮廓需要分配约 8千—1.5万；背景建筑模块建立约 8千／2千／数百面档位。栏杆、线缆和薄板先清理拓扑再减面，不能把所有模块直接压到原件 1%。 |
| **取消运行时重型几何整理** | 离线完成材质合并、烘焙和索引优化。街道按空间区段合并、实例分区；保留头眼必要动画结构即可。不采用本项目禁止的顶点量化捷径。 |
| **默认使用真正的基础管线** | 默认删除 DOF、SSR、全屏散射和横向拖光节点。仅保留必要抗锯齿、低分辨率 Bloom 与轻量调色。没有 AO／SSR 就移除对应 MRT；低档若改用空间抗锯齿，也可移除速度和历史缓冲。 |
| **限制内部像素总量** | 普通档从约 1280×720 内部渲染开始，按窗口比例适配，而非只限制 DPR。高档再开放 1080p。基础档渲染目标预算约 **60 MB**。不以严重糊掉模型为唯一优化手段。 |
| **简化光与体积** | 保留一个带深度遮挡的核心光束，低分辨率积分后上采样；移除重复光束。背景用高度雾。普通档雨约 1万—2万、水花 256—512；动态阴影优先给主角／主光，远处小道具停止投影。 |
| **烘焙昂贵的静态材质细节** | 机器人磨损、锈蚀、油污烘进图集，运行时只保留必要湿润响应。减少实时灯池规模，用招牌自发光和环境照明承担远处信息。 |
| **修资源生命周期与加载** | 默认新地面时不要先加载旧路面贴图；旧 `makeSurface` 缓存仍持有它们。释放不再使用的模型源数据和合并中间资源，正确处置 PMREM 临时资源。核心镜头先加载，远处模块后加载；限制并发解码，避免初始化峰值。 |
| **用资源白名单交付** | dist 只包含当前路线实际使用的文件，删去未引用的旧机器人、备用道具和 `m_pole` 等发布副本。首个可交互阶段恢复 **≤15 MB** 的项目预算，全程下载争取约 25—35 MB。生成原件保留在制作目录。 |

可执行的预算应是：纹理约 100 MB、渲染目标约 60 MB、几何与动画 GPU 数据约 40 MB、CPU 资产与工作数据约 120 MB，另给浏览器／驱动及峰值留至少 100 MB 余量。**这是约 420 MB 的预算方案，不是本轮已经实现的结果。** 不同浏览器的进程统计口径不同，不能把共享 GPU 进程和页面占用重复相加。

完成后由沙箱外实际验收：普通集显笔记本、冷启动、完整播放，分别记录下载量、峰值内存、GPU 时间、P95 帧时间和首次交互停顿。目标 60 FPS；做不到就继续减成本或明确稳定 30 FPS 档。M4 Pro 上某个旧版本的平均帧率不能替代这一项。

**4．对 Claude 这 10 小时工作方式的批评**

你把“宣传 Tripo 生成模型”做成了“给现有简模不断增加电影效果”。最关键的机器人不是 Tripo，猫不合格就藏进阴影，轿车换成一体生成模型后没有补上车门动画契约，背景模块生成了一批又一批，主角、门和前景道具却没有先通过近景验收。代码里一轮轮出现调磨损、调边光、调光束的补丁，说明你一直在处理症状，没有建立资产淘汰标准。你还把“生成成功、压成小 GLB、截图看着更亮”当成质量进展，忽略了输入本身的无支撑水桶、减面后的薄结构损坏、纹理解码成本和普通设备预算。猫与旧道具中也有 Codex 写的程序素材，责任不能按作者分摊：作为集成负责人，你必须把不合格物件挡在主镜头之外。这 10 小时最需要的不是再铺一条街、再加一种效果，而是先做出**一个能近看、能说明 Tripo 来源、放到普通电脑上也顺畅的机器人镜头**；它没有过关，扩场景就是扩大问题。
